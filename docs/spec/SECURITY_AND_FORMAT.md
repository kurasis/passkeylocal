# Security and Vault Format

## 1. Security boundary and threat model

The product encrypts a local, portable password database. It is designed to resist disclosure from a copied ciphertext file and detect unauthorized changes to that file, assuming a sufficiently strong master password and trustworthy executing code. It reduces accidental plaintext persistence and makes recovery independent of the PWA.

| Threat | Required treatment / remaining limit |
| --- | --- |
| Attacker copies a locked vault or backup | Strong password, Argon2id, standard KDBX encryption; offline guessing remains possible. |
| Attacker changes/truncates a backup | Authenticate the full header/body; fail closed; no partial recovery mode that skips authentication. |
| Browser data deletion or device loss | Verified external backups on a separate device/location; local snapshots alone cannot help. |
| Crash, failed disk write, concurrent tabs | Immutable encrypted blobs, transactionally switched head, conflict detection. |
| XSS, malicious imported strings, unsafe URLs | Plain-text rendering, CSP, no rich HTML, strict URL handling, no untrusted scripts. |
| Compromised host, build pipeline or dependency | Reduce exposure through controlled releases and dependency review; cannot guarantee protection once hostile code executes. |
| Malware, OS/browser exploit, unlocked-device access | Outside the protection guarantee. Locking and short secret exposure reduce ordinary accidental access only. |
| Clipboard, keyboard learning, screenshots, app-switcher previews | Minimize exposure; do not promise control the browser does not provide. |
| Valid old file replaces current file | Warn using local lineage/revision information when available. Offline files have no trusted global anti-rollback counter. |
| Forgotten master password | No server reset and no decryption bypass. A backup does not recover a missing password. |

Do not use claims such as “unhackable,” “military-grade,” “Face ID protected” in v1, “hardware-backed key” for an ordinary Web Crypto key, or “securely erased” for a deleted IndexedDB record. Do not claim that all data stays on the phone after a user deliberately exports/shares a backup.

## 2. Standard format instead of a new protocol

The authoritative container is a standard `.kdbx` file. The same bytes are stored in IndexedDB, used for encrypted rollback, and exported as backup. No device-bound secret, installation cookie, browser-generated opaque key, external manifest, network service, or Python-generated token is needed to decrypt an exported file.

This is a deliberate refinement of the initial AES-GCM concept discussed with the user: use the established KDBX encryption/authentication scheme rather than inventing a file format. AES-CBC by itself would be unacceptable. KDBX's authenticated construction and complete verification are required. Use established libraries for cryptographic operations and KDBX key composition; do not reimplement the protocol from this document. See sources S1–S6.

### Mandatory v1 writer profile

| Property | Value |
| --- | --- |
| File version | KDBX 4.1 |
| Outer cipher | AES-256-CBC, as defined by KDBX |
| Integrity | Standard header and block HMAC-SHA-256 checks |
| KDF | Argon2id, version 0x13 |
| KDF memory | 64 MiB = 67,108,864 bytes in the KDBX header |
| KDF iterations | 3 |
| KDF parallelism | 1 |
| Salt | Fresh 32-byte salt, generated by the library using a CSPRNG |
| Inner protected-field stream | Standard KDBX ChaCha20 protected-field mechanism |
| Compression | Disabled (`0`) |
| Credentials | Master password only; no key file or hardware factor |
| Attachments / custom binary icons | Not created; unsupported in the v1 interchange profile |
| Public custom header data | No product metadata or user content |

The memory/pass settings are product defaults chosen for a mobile workload, not a claim that RFC 9106 specifically recommends this exact tuple. Never reduce them silently because a phone is slow or short of memory. A device that cannot satisfy the required profile is unsupported for writing until an explicitly reviewed profile change is designed and cross-tested.

KDBX owns salt, seed, IV, inner-stream and subkey handling. Ensure the library refreshes the fields required by the standard on each save; never replace its RNG with a seeded test generator in a production build. A test must show repeated saves of identical logical content produce distinct valid ciphertexts.

### Browser Argon2 adapter

`kdbxweb` requires an Argon2 implementation to be supplied. The adapter must use the input bytes and requested raw output length; do not return a PHC encoded string or a hex string in place of bytes.

KDBX's memory parameter is in bytes; WASM APIs may accept KiB. Inspect the exact pinned `kdbxweb` adapter boundary: it may already convert the header value before calling the adapter. Convert once, at the correct boundary, and prove the mapping with fixtures. A factor-of-1,024 mistake must be caught by tests before any UI work. Require type Argon2id and version 0x13; reject unsupported variants instead of guessing.

Run KDF work off the UI thread and support cancellation by terminating the dedicated worker. Test the exact production WASM bundle on a physical iPhone. Browser Web Crypto does not natively provide Argon2id; the WASM dependency is part of the trusted application.

### Password handling

- Encode valid Unicode scalar values as UTF-8 using the library's standard password credential path.
- Do not trim, case-fold, normalize Unicode, remove spaces, or pre-hash the password before passing it to that API.
- Reject unpaired surrogate characters explicitly so JavaScript replacement behavior cannot disagree with Python.
- Preserve leading/trailing spaces; warn about them during creation but never modify them.
- Offer a long randomly generated passphrase and local strength guidance; do not query breach/strength services.
- New vaults require 16–1,024 Unicode scalar values; strength guidance must explain that length alone does not make a predictable password strong.
- Creation rejects NUL, CR and LF to avoid single-line input ambiguity; it does not remove these characters silently. Recovery accepts up to 4,096 UTF-8 bytes of valid password text and must not silently truncate an existing password. The Python exact-stdin path can recover unusual existing line-break-containing passwords; a PWA input limitation must be reported rather than changing the password bytes.
- For importing/recovering an otherwise supported existing file, allow nonempty passwords below the creation minimum and warn after success; never prevent recovery just because an old password is weak.
- Neither plaintext master password, transformed master key, nor a verifier that bypasses the KDF may be persisted. No “remember master password” toggle.
- Keep only the minimum credential material the library needs while unlocked. Clear input controls and drop references promptly; overwrite mutable buffers where possible.

Password changing requires the old password to be re-entered and successfully verified, even when the vault is already open. Validate a candidate saved under the new password before any head switch. Follow the backup/rotation sequence in the recovery document. Existing exported files still require their original passwords.

## 3. Reader compatibility and hostile-input limits

The v1 PWA and Python tool guarantee their own writer profile above. They may accept KDBX 4.0 files using the same supported suite and data subset. They do not claim universal support for every KeePass plugin or legacy database. An ordinary compatible KeePass implementation must nevertheless be able to open files created by this app; verify that as a release gate.

The file generally does not identify which combination of password/key file was originally used. The tool supports password-only credentials and must not pretend to reliably diagnose a missing key file from an authentication failure.

Supported reader KDF envelope: Argon2id v0x13, memory 64–256 MiB in whole KiB, iterations 3–10, parallelism 1–4, salt length 16–64 bytes. Writers still use the fixed default tuple. Treat stronger/out-of-envelope files as unsupported or too expensive, not corrupt. Do not silently rewrite their settings. V1 does not offer an “ignore security checks” flag.

Normal editing of an accepted imported file preserves its existing KDF settings within this envelope. The default tuple applies to newly created vaults. Any deliberate KDF change is an explicit migration with backup and interoperability checks; do not weaken a stronger imported profile incidentally when saving.

Before invoking the KDF or allocating a large buffer, a bounded structural preflight must check:

1. File size at most 16 MiB; signatures and supported version; cumulative outer-header size at most 64 KiB.
2. Header field lengths, dictionary types, arithmetic overflow, duplicate critical fields/keys, missing terminators and inconsistent declared sizes.
3. The allowed cipher, compression and KDF profile; reject gzip before decompression, unknown algorithms and unsupported public provider data.
4. Numeric KDF limits before converting 64-bit values to JavaScript numbers. Use safe integer/BigInt handling.
5. Block lengths within the remaining file and product maximum; valid final block and no unexplained trailing bytes.

These checks only limit resource abuse; unauthenticated header values remain untrusted until the library verifies them. Computing an unkeyed checksum does not authenticate a vault.

After KDF, authenticate all required data before making any plaintext available to the UI/CLI. Wrong-password and authentication failures must not cause overwrite, reset, partial export or automatic creation of an empty database. Use “Unable to unlock: password is incorrect or the file is damaged” where the cause cannot be reliably distinguished. Clearly identify unsupported algorithms/limits separately.

Reject unsupported attachments/custom binary icons and compressed payloads rather than dropping them. For authenticated XML, forbid DTDs, entity declarations, external entities, XInclude and network resolution; reject them before general XML parsing where the dependency permits. Enforce the size/depth/record limits. If the chosen library cannot enforce a needed parser control, fix or replace that integration before release; do not merely document that an unchecked parser exists.

Do not accept malformed XML by “repairing” it. Unknown encrypted fields within a supported schema must be preserved losslessly; if they cannot be preserved, offer read-only recovery/export of the original file and refuse a destructive write. A future `LocalVault.SchemaVersion` must not be silently downgraded.

## 4. Plaintext lifetime and lock behavior

Use a small in-memory domain layer. Do not persist decrypted state using React stores, query caches, state-devtool plugins, localStorage, sessionStorage, URL history, Cache Storage, worker messages stored on disk, or crash reports. Ensure names/notes and search queries receive the same treatment as passwords.

Default lock behavior:

- Manual Lock: immediate redaction and session invalidation.
- `visibilitychange` to hidden or `pagehide`: immediately redact, invalidate the unlock session, discard uncommitted drafts and request worker termination.
- Inactivity while visible: 2 minutes by default; allow 30 seconds, 1, 2, or 5 minutes, with no “never” option in v1.
- `pageshow`, foreground return, process restart and back/forward restoration: require unlocking again.

Do not rely on background timers or unload handlers to save data. At each operation and foreground transition check whether the session is still valid. Late asynchronous responses from a prior session must be ignored. A native file/share picker may also trigger hiding: prepare only ciphertext before opening it, lock if hidden, and require re-unlock after return.

When locking, unmount/redact sensitive views, clear search text and derived indexes, release object references, clear mutable buffers when feasible, and terminate dedicated workers. Do not promise exact zeroization of JavaScript/Python strings, browser memory, swap, or OS snapshots. `ProtectedValue` wrappers are not a security boundary against running malicious code.

Secrets are hidden by default. A reveal ends when the view changes or session locks. Screen capture and app-switcher redaction cannot be guaranteed from a PWA; test redaction behavior but describe it as best effort.

Clipboard writes require an explicit action. Never read the system clipboard automatically. Show a short reminder that the copied password may remain in the clipboard or sync through OS features. A best-effort clear action may be offered where permitted, but must not promise automatic clearing, silently overwrite unrelated new clipboard contents, or delay lock waiting for clipboard access.

## 5. Web security and deployment

Render imported content as text, never raw HTML or Markdown with HTML enabled. Avoid `dangerouslySetInnerHTML`. Treat URLs, custom field names, titles, filenames and terminal output as untrusted. Do not execute `javascript:`, `data:`, file paths, auto-type instructions, field-reference expansion, plugin commands, or embedded XML instructions.

Clickable entry URLs allow HTTPS; an HTTP link needs a clear warning. Reject embedded username/password URL credentials and other schemes. Open deliberate external navigation with `noopener noreferrer` and never append vault data to the address. Do not prefetch, preview or resolve stored URLs.

Deploy response headers using the static host's real header configuration. Start from:

```text
Content-Security-Policy:
  default-src 'none';
  script-src 'self' 'wasm-unsafe-eval';
  style-src 'self';
  img-src 'self';
  font-src 'self';
  connect-src 'self';
  worker-src 'self';
  manifest-src 'self';
  object-src 'none';
  base-uri 'none';
  form-action 'none';
  frame-ancestors 'none'
Referrer-Policy: no-referrer
X-Content-Type-Options: nosniff
Permissions-Policy: camera=(), microphone=(), geolocation=(), payment=(), usb=()
```

This is a baseline to test, not a claim that every bundler/library already works under it. Use external stylesheets instead of broadly allowing inline styles. If WASM needs `wasm-unsafe-eval`, retain that narrowly scoped allowance; never widen to general `unsafe-eval`. Avoid blob workers; load a bundled worker URL. Blob URLs used only for user-initiated encrypted downloads are not a reason to loosen script-src. Serve appropriate JS/WASM MIME types, HTTPS and HSTS where operationally appropriate. Set worker/script headers too; verify headers on actual deployed responses, not just development mode.

No analytics, ads, remote fonts, crash-reporting SDKs, external script tags, remotely fetched configuration, breach checks or favicon services. No application request carries record content, master passwords, keys, queries or backup bytes. Build tooling and the host may make separate infrastructure requests, which must be identified in network tests. Browser-initiated service-worker update traffic must not be confused with vault synchronization.

`connect-src 'self'`, HTTPS, hashes downloaded from the same host, and a user-confirmed update do not defend against a hostile origin that can replace both code and policy. Document that dependency, use a dedicated stable origin, protect host/DNS/build credentials, review release diffs, and keep independent offline recovery files. Do not describe service-worker caching as a permanent trusted-code pin.

After initial installation and offline readiness, all vault operations must work in airplane mode. A domain change is an origin change: local storage does not follow automatically. Provide migration by verified export/import, never by pretending that the new domain sees the old database.

## 6. Operational requirements

- A production build excludes development tools, demo credentials, debug endpoints and remote logging.
- Exceptions shown to users contain a safe code and actionable message; never serialize credential objects, XML, passwords or record text into errors.
- Dependency updates are reviewed and rerun the entire interop/tamper suite; no automatic deploy of dependency-bot changes.
- Maintain a bill of materials, lockfiles, source/license notices and a record of the exact KDBX/WASM/Python versions tested together.
- The password generator uses `crypto.getRandomValues` with unbiased selection, with a default of 24 characters. Never use Math.random. Any passphrase wordlist is bundled and its entropy calculation documented.
- Do not make unsupported claims that rate-limiting the UI prevents offline guessing; a copied file bypasses that UI.
- Provide a short user recovery guide and a developer security review checklist tied to the tests, not a generic promise of security.
